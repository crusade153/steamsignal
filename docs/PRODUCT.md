## 0. 한 문장

> Steam 이 보여 주지 않는 **변화**를 보여 주는 사이트.
> 순위표는 어디에나 있다. 우리는 10분마다 직접 기록한 시계열로 **"어제와 무엇이 달라졌는가"** 에 답한다.

이 문장이 모든 판단의 기준이다. 어떤 기능을 넣을지 고민될 때, 그것이 "변화"를 보여 주는지 묻는다.
현재값만 보여 주는 기능은 다른 사이트도 다 한다.

## 1. 누가, 왜 오는가

세 상황을 상정한다. 순서는 중요도다.

| # | 상황 | 필요한 답 | 지금 상태 |
| --- | --- | --- | --- |
| 1 | **"이 게임 지금 할 만한가"** — 살까 말까 고민 중 | 사람이 있나, 늘고 있나 줄고 있나, 최근 평이 어떤가 | 게임 상세·리뷰 추이가 답한다 |
| 2 | **"내가 찜한 게 싸졌나"** — 가격 대기 중 | 지금이 최저가인가, 할인은 언제 끝나나, 언제 알려 주나 | 위시리스트·`/deals/all-time-low`와 한국시간 종료일이 답한다. 알림은 아직 꺼져 있다 |
| 3 | **"요즘 뭐가 뜨나"** — 다음 게임을 찾는 중 | 오르고 있는 게임, 새로 들어온 게임 | `/rising` 이 답한다 |

**1번이 검색 유입, 2번이 재방문, 3번이 체류시간을 만든다.** 셋의 성격이 다르므로 지표도 다르게 본다.

## 2. "엔터프라이즈급"의 정의

캐치프레이즈로 두면 아무것도 결정하지 못한다. **네 기둥으로 분해한다.**
장식은 네 번째가 아니라 네 기둥 전부에 얹히는 것이며, 기둥 자체가 아니다.

### 2-1. 신뢰성 — "이 숫자는 맞다"

엔터프라이즈 제품과 취미 프로젝트를 가르는 첫 번째 선이다. 화려함과 무관하다.

**되어야 하는 상태**
- 화면의 모든 숫자에 **언제 잰 값인지**가 붙어 있다. (일부 적용됨 — 게임 상세의 "마지막 갱신")
- 모르는 값은 **모른다고 쓴다.** 결측을 0 으로 만들지 않는다. (규율로 확립됨)
- 표본이 얇으면 **얇다고 밝힌다.** "7일 평균"이라 써 놓고 3일을 평균하지 않는다. (`/rising` 이 이미 이렇게 한다)
- 파이프라인이 멈추면 **사용자보다 먼저 우리가 안다.** (`watchdog` 으로 확립됨)
- 수집 상태를 **공개한다.** 마지막 수집 시각, 커버리지, 결손 구간을 사용자가 볼 수 있는 페이지.
  이걸 공개하는 사이트는 데이터를 숨기지 않는다는 신호를 준다.

**측정**
- `watchdog` 무경보 연속 일수 — 30일이 목표
- 스냅샷 결손율 — 하루 144 tick 중 실제 기록된 비율. **99% 이상**
- 상세 수집 한 바퀴 도는 데 걸리는 시간 — **2시간 이내**

### 2-2. 정보밀도 — "한 화면에서 판단이 끝난다"

엔터프라이즈 대시보드의 실체는 예쁜 여백이 아니라 **정보가 촘촘한데도 읽힌다**는 것이다.

**되어야 하는 상태**
- 목록의 한 행에서 **판단이 끝난다.** 스파크라인은 원시 동접의 모양이 아니라 비교 가능한 변화율을 보여 준다.
  첫 24시간은 추적군 내 비중 변화, 이후는 전일 동시간 대비, 일 롤업이 쌓이면 일평균 전일 대비다.
- 스파크라인의 세로축은 모든 게임이 같은 **±50%**다. 행마다 최소~최대를 따로 늘리지 않는다.
  작은 흔들림과 큰 사건이 같은 높이로 보이면 그림은 예쁘지만 비교 도구는 아니다.
- 순위 변동을 **기호로** 보여 준다. `▲3` `▼1` `NEW`. 숫자표에서 눈이 가장 먼저 가는 것이다.
- 조건부 색상은 **의미가 있을 때만.** 지금 평가 75/50 기준 색은 좋은 예다. 색을 늘리지 않는다.
- 정렬·필터·페이지가 **URL 에 남는다.** 공유·북마크·뒤로가기가 되어야 도구다. (홈은 이미 그렇다)
- 표의 열은 **어느 페이지에서나 같은 순서**로 나온다.

**측정**
- "이 게임 할 만한가"에 답하는 데 필요한 클릭 수 — 현재 1회(목록→상세), 목표 **0회**(목록에서 끝)
- 첫 화면(스크롤 없이)에 보이는 게임 수 — 데스크톱 **6개 이상**, 모바일 **3개 이상**

### 2-3. 일관성 — "어느 페이지를 가도 같은 규칙"

페이지를 추가할수록 어긋나는 것이 취미 프로젝트의 전형적 붕괴 경로다.

**되어야 하는 상태**
- 색·간격·타이포그래피가 **토큰**으로 정의되고, 페이지는 토큰만 쓴다.
  지금 `styles.css` 는 미니파이된 한 줄이라 사람이 못 고친다. 이게 붕괴의 예고다.
- 빈 상태 문구가 **같은 형식**을 따른다 — "없다"가 아니라 "**언제** 채워지는지".
  (현재 방식이 옳다. 시각적으로만 정돈하면 된다)
- 새 페이지를 만들 때 **CSS 추가량이 0 에 수렴**한다. 이게 일관성의 진짜 측정법이다.

**측정**
- 새 페이지 1개당 추가되는 CSS 줄 수 — **5줄 이하**
- 하드코딩된 색상 값(`#` 리터럴)의 개수 — 토큰 정의부 외에 **0**

### 2-4. 응답성 — PC·모바일 동등

**"모바일에서도 열린다"가 아니라 "모바일에서도 1급"이다.** 이게 운영자가 정한 선이다.

**되어야 하는 상태**
- 390px 에서 **정보가 첫 화면에 보인다.** 가로 스크롤로 미루는 것은 통과가 아니다.
- 좁은 화면에서는 표를 **카드로 전환**한다. 행 하나 = 카드 하나, 지표는 2열 그리드.
- 내비게이션이 **뭉개지지 않는다.** 390px 회귀는 수정했고, e2e가 내비 높이까지 검사한다.
- 터치 목표는 **44px 이상.**

**측정 — 세 폭에서 전부 통과해야 한다**

| 폭 | 기준 |
| --- | --- |
| 390px (모바일) | 가로 넘침 0 · 내비 1줄 · 첫 화면에 게임 3개 이상 · 표 가로 스크롤 불필요 |
| 768px (태블릿) | 가로 넘침 0 · 표 그대로 읽힘 |
| 1440px (데스크톱) | 첫 화면에 게임 6개 이상 |

> e2e는 `scrollWidth <= innerWidth`뿐 아니라 내비 높이와 첫 화면의 서로 다른 게임 수도 함께 잰다.
> 내비 뭉개짐은 넘치지 않은 채 발생할 수 있으므로 높이 검사를 빼면 안 된다.

## 3. 재방문 설계

**재방문의 조건은 하나다 — 어제와 오늘이 다르고, 그 차이가 나와 관련 있을 것.**

두 조건이 모두 필요하다. 매일 바뀌어도 나와 무관하면 안 오고, 나와 관련 있어도 안 바뀌면 안 온다.

### 퍼널

```
검색 유입 → 가치 인지 → 개인화(위시리스트) → 알림 등록 → 재방문 루프
   1번 상황     "이 숫자 어디서 왔지"   "담아 두자"      "알려 줘"      "또 뭐 바뀌었나"
```

각 단계에서 이탈하는 이유와 대책:

| 단계 | 이탈 이유 | 장치 | 상태 |
| --- | --- | --- | --- |
| 유입 → 인지 | "다른 데도 있는 숫자네" | 우리만 있는 것을 먼저 보여 준다 — 추세, Δ, 리뷰 추이 | 부분 |
| 인지 → 개인화 | 담을 이유가 없음 | 담으면 **무엇이 좋아지는지** 그 자리에서 말한다 | 미흡 |
| 개인화 → 알림 | 계정 만들기 싫음 | 이메일 하나, 계정 없음, 언제든 해지 | 코드 완성 · 미가동 |
| 알림 → 재방문 | 메일이 시끄러움 | 조건 충족 시에만, 여러 건은 한 통으로 | 설계됨 |

### 장치 (효과 큰 순서)

1. **이메일 알림 가동.** 코드도 DB 도 준비됐고 환경변수 2개만 남았다.
   **재방문 장치 중 투자 대비 효과가 압도적으로 크다** — 사용자가 우리를 기억할 필요가 없어진다.
2. **위시리스트에 Δ.** 지금은 현재값만 보여 준다. "어제 대비 +12%", "3일 전보다 5,000원 내림"이
   보이면 담아 둔 사람은 매일 열어 볼 이유가 생긴다. `player_daily` + `price_events` 로 계산된다.
   상태는 계속 localStorage 에만 둔다(CLAUDE.md 규칙 10).
3. **홈 첫 화면의 "오늘의 변화".** 지금 홈은 TOP 100 순위라 어제와 거의 같다.
   순위가 가장 많이 오른 게임 / 새로 진입한 게임 / 오늘 시작된 할인을 위로 올린다.
4. **순위 변동 화살표.** 가장 값싼 장치. `player_daily.best_rank` 로 계산된다.
5. **주간 리포트.** 월요일 아침 1통. 코드 완성됨.

## 4. 커버리지 — 100개에서 200개로 (2026-09-06 달성)

> **운영자가 목표를 200개로 정했다.** 300개는 그다음이다. 아래의 계산과 방법 비교는
> 그대로 유효하고, 실제로 고른 것은 **세 번째(차트 이력 누적) + 개별 동접 조회**다.
> 결과는 이렇다 — 추적 200개, 한 틱에 196개 기록, 사이트맵 URL은 확장 직후 160 → 257개,
> 현재 실측 259개다.
>
> 차트가 100개만 주므로 **차트 밖 100개는 appid 하나씩 `GetNumberOfCurrentPlayers` 로 묻는다.**
> 로스터를 몇 달 기다리지 않고 채우기 위해 `discover` 잡이 스토어 판매 상위에서 후보를 받는다.
> 자세한 것은 [DATA-PIPELINE.md §3](DATA-PIPELINE.md).

### 확장 전에는 왜 100개였나

Steam 의 `mostplayed` 차트가 **정확히 100개만 준다.** `lib/steam.mjs` 가 `.slice(0, 100)` 한다.
`chartTop()` 의 상한 200 은 방어값이고 실제 호출은 100 이다.

확장 전 DB에는 109개가 있었고, 9개는 **차트에서 내려간 앱**이었다. `apps` 행은 지우지 않으므로
시간이 지나면 자연히 늘어난다. 하지만 그 앱들은 `rank` 가 NULL 이고 **동접 수집이 멈춘다** —
차트 잡이 차트 안의 100개만 스냅샷을 찍기 때문이다. 그래서 상세 페이지의 차트가 어느 날 끊긴다.

**커버리지 확대의 숨은 이득이 이것이다.** 300개를 추적하면 차트에서 잠깐 내려간 게임의
시계열이 끊기지 않는다. 끊기지 않은 시계열은 "예전엔 잘나갔는데 지금은" 이라는 우리만의 이야기가 된다.

### 300개로 가려면 결정해야 하는 것

**차트 밖 200개를 어디서 가져올 것인가.** 후보:

| 방법 | 얻는 것 | 대가 |
| --- | --- | --- |
| `ISteamUserStats/GetNumberOfCurrentPlayers` | appid 하나당 현재 동접. **공식 API** | 앱당 요청 1회 — 300개면 10분마다 300 요청 |
| SteamSpy API | 상위 목록·소유자 추정 | 비공식, 정확도·안정성 미검증 |
| 차트 이력 누적 | 추가 소스 불필요 — 한 번이라도 100위 안에 든 게임을 계속 추적 | 300개까지 **몇 달** 걸린다. 대신 공짜 |

**세 번째가 가장 저렴하고 위험이 없다.** 이미 `apps` 에 행이 쌓이고 있으므로,
차트 잡이 "차트 100개 + 최근 N일 안에 차트에 있었던 앱"을 함께 찍도록 바꾸면 된다.
1~2번은 그것으로 부족할 때 검토한다.

### 300개일 때의 비용 (실측 기반 추정)

| 항목 | 100개 (비교 기준) | 300개 | 비고 |
| --- | --- | --- | --- |
| `player_snapshots` (7일) | 10만 행 · 12MB | 30만 행 · **36MB** | 보관정책이 잡아 주므로 **고정** |
| `player_hourly` (90일) | 21.6만 행 · 24MB | 64.8만 행 · **73MB** | 고정. 가장 큰 테이블이 된다 |
| `player_daily` (영구) | 4MB/년 | **13MB/년** | 누적 |
| `review_daily` (영구) | 3MB/년 | **10MB/년** | 누적 |
| **1년 뒤 DB 총량** | ~45MB | **~135MB** | Neon 무료 500MB 의 **27%** |
| 상세 수집 한 바퀴 | 55분 (batch 20) | 2.5시간 (batch 20) | **batch 를 40으로 올려야** 1.25시간 |
| Steam 요청량 | 40req/10분 | 80req/10분 | 알려진 한계(≈400req/10분) 안 |
| 사이트맵 URL | 163 | **400~500** | 검색 유입은 URL 수에 거의 비례한다 |

**결론: 용량은 문제가 아니다.** 3년을 돌려도 200MB 아래다.
정말로 봐야 할 것은 **Vercel Fluid Active CPU**(월 4시간)이고, 이건 아직 실측이 없다.
100개로 하루 돌려 본 뒤 3배 해서 판단한다.

여유가 부족해지면 순서대로 줄인다: `player_hourly` 보관 90일 → 60일(73MB → 49MB) →
`details` batch 축소 → 커버리지 축소.

## 6. 순서

**한 번에 다 하지 않는다.** 앞 단계가 뒷 단계의 전제다.

**Phase 1 — 깨진 것부터.** 모바일 내비 회귀, 표의 카드 전환, e2e 에 뭉개짐 검사.
*깨진 화면 위에 기능을 쌓으면 둘 다 나빠진다.*

**Phase 2 — 재방문 장치.** 이메일 알림 가동(환경변수 2개), 위시리스트 Δ, 순위 변동 화살표.
*가장 싼 비용으로 가장 큰 효과가 나는 구간이다.*

**Phase 3 — 정보밀도.** 목록에 스파크라인과 Δ, 홈의 "오늘의 변화".
*여기서부터 "다른 Steam 미러와 다르다"가 눈에 보인다.*

**Phase 4 — 커버리지 300개.** 차트 이력 누적 방식으로 시작. batch 상향과 함께.
*Phase 3 까지 되면 게임 하나하나가 더 가치 있어지므로, 그때 늘리는 것이 순서다.*

**Phase 5 — 일관성·마감.** 디자인 토큰 정리, 빈 상태 정돈, 로딩 스켈레톤.

## 8. 계정 — 하지 않기로 했다가, 하기로 한 것

2026-09-06, 운영자가 §7 의 '회원가입 안 함'을 뒤집었다. **그 결정에 조건이 붙었다.**

> **회원 가입과 관리는 강제사항이 아니고 자율사항이고, 사이트는 누구나 이용 가능해야 한다.**

이 문장이 계정 기능의 설계 전부를 정한다.

### 지켜야 하는 선

- **로그인해야 볼 수 있는 화면을 만들지 않는다.** 순위·급상승·할인·게임 상세·위시리스트·
  가격 알림 — 전부 계정 없이 지금까지와 똑같이 동작한다. `check.mjs` 가 익명 접근을 검사한다.
- **계정을 상단 내비에 올리지 않는다.** 맨 위에 '로그인'이 있으면 사람들은 그걸
  '가입해야 쓰는 사이트'로 읽는다. 푸터와 계정 화면에서만 안내한다.
- **로그인·가입 화면이 "선택 사항"이라고 직접 말한다.** 거기가 사용자가
  "안 하면 못 쓰나"를 가장 크게 의심하는 자리다. e2e 가 그 문구의 존재를 검사한다.
- **계정이 주는 것은 하나뿐이다** — 담아 둔 게임을 기기 사이에서 이어 주는 것.
  기능을 계정 뒤로 옮기는 변경은 이 결정의 범위 밖이다.

### 대가 (§7 에서 걱정했던 것)

계정을 만드는 순간 개인정보 부담이 생긴다. 그건 없어지지 않았고, 대신 이렇게 줄였다.

| 부담 | 어떻게 줄였나 |
| --- | --- |
| 비밀번호 유출 | 원문을 저장하지 않는다(scrypt). 해시 문자열이 파라미터를 들고 있어 나중에 비용을 올릴 수 있다 |
| 세션 탈취 | 쿠키에는 난수, DB 에는 그 해시. HttpOnly · SameSite=Lax · https 에서 Secure |
| 주소 존재 확인 | 가입·로그인 실패 문구가 하나다. 없는 주소에도 해시를 계산해 응답 시간을 맞춘다 |
| 무차별 대입 | IP 를 저장하지 않으므로 계정별 실패 횟수와 잠금으로만 막는다(8회 / 15분) |
| 추적 우려 | 접속 IP·브라우저 정보를 기록하지 않는다. 쿠키는 로그인 유지 하나에만 쓴다 |
| 탈퇴 후 잔존 | 행을 남기지 않는다. 세션·저장 목록은 CASCADE 로 함께 사라진다 |

### 측정

| 지표 | 목표 |
| --- | --- |
| 로그인을 요구하는 화면 수 | **0** — 하나라도 생기면 이 결정을 어긴 것이다 |
| 계정 없이 쓸 수 있는 기능 비율 | **100%** (동기화 제외) |
| 계정 삭제까지 걸리는 클릭 | **2** (계정 화면 → 비밀번호 입력 → 삭제) |

## 9. 멀티플랫폼 — 콘솔판 Steam 미러가 아니라 관심 변화 레이어

장기적으로 Xbox·PS5·Nintendo Switch 2를 별도 카테고리로 확장한다. 다만 세 플랫폼에는
Steam Web API처럼 누구나 전체 카탈로그의 실시간 동접·가격을 읽는 공식 무료 API가 없다.
따라서 없는 숫자를 추정하거나 비공개 스토어 API에 기대지 않고, 플랫폼 공통으로 관측 가능한 변화를 만든다.

### 사용자가 받는 답

| 질문 | 결합할 데이터 | 만들 정보 |
| --- | --- | --- |
| 지금 관심이 커지는 게임인가 | Steam 동접 + Twitch 시청자 + Wikipedia 조회 | 관심 선행·입소문·하이프 과열 |
| 어느 플랫폼에 언제 나오나 | 공통 게임 ID + 플랫폼별 출시일 | 30/90일 출시 레이더·동시 출시·지연 출시 |
| PC에서 검증된 뒤 콘솔로 오나 | Steam 시계열 + 콘솔 출시일 | PC 선출시 후 콘솔 이동과 재상승 |
| 관심이 실제 플레이로 이어졌나 | 시청·검색 변화와 Steam 동접 변화 | 하이프 대비 플레이 전환 |

### 플랫폼별로 실제 얻을 수 있는 것

기획을 시작하기 전에 이 표를 먼저 본다. **동시접속자 열이 전부 ✕ 라는 것이 이 절의 전제다.**
콘솔 3사는 전체 카탈로그의 실시간 동접을 공개한 적이 없고, 공식 API 는 승인된 개발사가
자사 타이틀만 보는 용도다. "콘솔 동접 대시보드"는 만들 수 있는 물건이 아니라 추정치다.

| | 동시접속자 | 가격·할인 | 출시일·카탈로그 | 인기 순위 |
| --- | --- | --- | --- | --- |
| **Steam** (지금) | ✅ 공식 무료 API · 10분 | ✅ 한국 가격 공식 | ✅ | ✅ 차트 100 |
| **Xbox** | ✕ 존재하지 않음 | △ 스토어 카탈로그 엔드포인트가 **미문서** | △ 같은 경로 | △ Game Pass 입·퇴점(공식 발표) |
| **PlayStation** | ✕ | △ 스토어 GraphQL 이 **미문서** | △ 같은 경로 | △ 월간 다운로드 순위(**순위만, 숫자 없음**) |
| **Switch** | ✕ | △ eShop 가격 엔드포인트가 **미문서** | △ 검색 엔드포인트 | △ 분기 IR 판매량(공식, 분기 단위) |

그래서 콘솔에서 **가져오는 것은 사실(출시일·가격·발표)뿐이고, 시계열은 플랫폼 공통 공개
데이터에서 만든다.** 미문서 엔드포인트는 예고 없이 막히므로 **핵심 의존성으로 두지 않는다** —
없으면 페이지가 죽는 게 아니라 그 칸이 `집계 전`이 된다(§ 결측 규율과 같은 원칙).

### 대신 만드는 것 — Steam 미러가 못 만드는 네 지표

콘솔 동접 대신, 플랫폼과 무관하게 **공식·무료로** 열려 있는 것을 쓴다.
Twitch Helix(게임별 시청자) · Wikimedia Pageviews(일 단위 조회수, 키 불필요) ·
Wikidata SPARQL(CC0, 플랫폼별 출시일과 스토어 ID 매핑) · 각 사 공식 발표.

| 지표 | 계산 | 이 사이트만 만들 수 있는 이유 |
| --- | --- | --- |
| **하이프 대비 실제 플레이** | Twitch 시청자 변화 ÷ Steam 동접 변화 | 우리가 직접 기록한 10분 동접 시계열이 분모다. 미러는 분모가 없다 |
| **관심 선행** | 위키·시청 상승이 동접 상승보다 며칠 앞섰나 | 같은 게임의 두 시계열을 같은 축에서 봐야 나온다 |
| **출시 레이더** | 공통 `game_id` + 플랫폼별 출시일 | 30/90일 내 출시·동시 출시·지연 출시 |
| **플랫폼 이동** | Steam 시계열 + 콘솔 출시일 | PC 선출시 뒤 콘솔로 갈 때의 재상승 |

앞의 둘은 **Steam 동접 시계열을 이미 갖고 있는 쪽만** 만들 수 있다. 멀티플랫폼 확장의
값은 콘솔 데이터를 늘리는 데 있는 게 아니라, 이미 가진 Steam 시계열을 분모로 쓰는 데 있다.

### 데이터 원칙

1. `Steam 플레이어`, `Twitch 시청자`, `Wikipedia 조회`를 이름부터 분리한다. 합성 점수를 쓰더라도
   원재료와 계산식을 함께 공개한다.
2. 플랫폼 공통 `game_id`를 만들고 Steam appid·Twitch game ID·Wikidata ID를 매핑한다.
   제목만 같은 게임을 자동 병합하지 않는다.
3. 모든 값에 `source`·`observed_at`·라이선스·결측 상태를 둔다. 결측은 계속 0이 아니다.
4. Wikidata/Wikimedia는 캐시해 하루 단위로, Twitch는 별도 크론으로 수집한다. 사용자 요청에서 외부 API를 부르지 않는다.
5. 콘솔 동접·실시간 가격은 합법적이고 안정적인 공급자가 생기기 전까지 제공하지 않는다.
6. **새 지표에는 보관정책을 같이 만든다.** 시간 단위 시계열을 영구 보관하는 순간
   저장소 예산이 무너진다. `player_*` 와 같은 3단(원시 → 시간 → 일) 규율을 그대로 따른다.

### 저장소 비용 — 예산 안에 들어온다

"콘솔까지 하면 용량이 감당되나"의 답이다. 추적 200개 기준, 보관정책을 처음부터 같이 만들면
관심 레이어 전체가 **초기 40MB + 연 10MB** 수준이다.

| 새 데이터 | 주기 | 보관 | 행 | 크기 |
| --- | --- | --- | --- | --- |
| Twitch 시청자(시간) | 1시간 | 90일 | 43만 | ~30MB |
| Twitch 시청자(일) | 1일 | 영구 | 7.3만/년 | ~5MB/년 |
| Wikipedia 조회수 | 1일 | 영구 | 7.3만/년 | ~5MB/년 |
| 플랫폼 출시일 | 변경 시 | 영구 | 800 | 1MB 미만 |

**보관정책 없이 Twitch 를 시간 단위로 영구 저장하면 연 175만 행(~120MB)** 이라
2년이면 예산이 넘는다. 차이는 데이터가 아니라 보관정책에서 난다.

저장소 예산 자체는 이제 코드에 고정돼 있지 않다 — `DB_SIZE_BUDGET_MB` 하나로 요금제를
따라가고, 사용률이 70%·85% 를 넘으면 보관 기간이 자동으로 좁아진다
([DATA-PIPELINE §2-1](DATA-PIPELINE.md)). 그래서 **커버리지·새 지표를 늘릴 때
"용량이 터질까"가 아니라 "예산의 몇 %를 쓸까"로 물을 수 있다.**

### 순서 — 새 URL 은 마지막에 연다

1. **공통 `game_id` + 플랫폼별 출시일부터.** 지금 200개에 대해서만, 새 페이지 없이
   게임 상세에 "다른 플랫폼 출시" 한 줄을 붙인다. 매칭 정확도를 실제로 재는 가장 싼 방법이고,
   Wikidata 커버리지가 낮으면 여기서 멈추면 된다.
2. **Twitch 시청자 시계열.** 여기서 `하이프 대비 실제 플레이`와 `관심 선행`이 나온다.
   보관정책(시간 90일 → 일 영구)을 같은 커밋에서 만든다.
3. **매칭이 신뢰할 만해진 뒤** `/platform/xbox` · `/platform/ps5` · `/platform/switch-2` 를
   출시 레이더와 관심 변화 중심으로 연다. 콘솔 동접이나 가격을 추정해 만들지 않는다.

순서를 뒤집으면 안 되는 이유는 얇은 조합 페이지 규율과 같다 — 사이트맵에 올렸는데 내용이
비는 URL 이 생기면 색인 전체가 손해를 본다. 3번은 **1·2번이 검증된 뒤에만** 시작한다.
